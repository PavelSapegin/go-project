# Каталог фильмов (PostgreSQL + Redis)

HTTP/gRPC-сервис каталога фильмов с основным хранилищем в PostgreSQL, автоматической синхронизацией со стендом при старте, обратным поисковым индексом и кэшированием поисковых ответов в Redis.

## 1. Запуск PostgreSQL и Redis

Быстрее всего поднять зависимости через Docker (учётные данные и порты совпадают со значениями по умолчанию в приложении):

```bash
# PostgreSQL
docker run -d \
  --name movie-postgres \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=password \
  -e POSTGRES_DB=postgres \
  -p 5432:5432 \
  postgres:16-alpine

# Redis (без пароля)
docker run -d \
  --name movie-redis \
  -p 6379:6379 \
  redis:7-alpine
```

Проверка готовности:

```bash
docker exec movie-postgres pg_isready -U postgres -d postgres
docker exec movie-redis redis-cli PING
```

## 2. Переменные окружения

Переданные переменные окружения имеют приоритет над значениями по умолчанию.

| Переменная | Описание | Значение по умолчанию |
|---|---|---|
| `MOVIE_BASE_URL` | Базовый URL стенда фильмов | `https://homeworksite.site` |
| `HTTP_ADDR` | Адрес и порт HTTP-сервера | `:8080` |
| `DATABASE_URL` | DSN подключения к PostgreSQL | `postgres://postgres:password@localhost:5432/postgres?sslmode=disable` |
| `REDIS_ADDR` | Адрес Redis в формате `host:port` (без пароля) | `localhost:6379` |

gRPC-сервер запускается на порту `:50051`.

## 3. Применение миграций

SQL-миграции находятся в каталоге `migrations/` (`001_create_movie_table.sql`, таблица `movies` с полями `id`, `title`, `year`, `director`) и применяются **автоматически при запуске приложения** с помощью `goose`.

Отдельный ручной шаг для накатывания миграций не требуется — достаточно запускать приложение из корня Go-модуля (рядом с папкой `migrations/`).

## 4. Запуск приложения

Выполните из каталога Go-модуля (`task6/`):

```bash
go run ./cmd/main.go
```

Или с явным указанием переменных окружения:

```bash
MOVIE_BASE_URL="https://homeworksite.site" \
HTTP_ADDR=":8080" \
DATABASE_URL="postgres://postgres:password@localhost:5432/postgres?sslmode=disable" \
REDIS_ADDR="localhost:6379" \
go run ./cmd/main.go
```

При старте сервис последовательно:
1. Дожидается готовности PostgreSQL и применяет миграции `goose`.
2. Дожидается готовности Redis.
3. Синхронизирует фильмы со стенда в PostgreSQL без создания дублей.
4. Перестраивает обратный индекс в Redis по всем фильмам из PostgreSQL и очищает старый кэш поисковых ответов.
5. Запускает HTTP- и gRPC-серверы (после полной готовности индекса).

## 5. Структура индекса и кэша в Redis

Ключи обратного индекса и кэша разделены по префиксам, чтобы при очистке кэша индекс оставался нетронутым:

### Обратный индекс
- **Формат ключа:** `idx:word:<слово>`
- **Тип данных в Redis:** `Set` (множество)
- **Значения:** строковые представления `id` фильмов, в `title` или `director` которых встречается данное слово.
- **TTL:** отсутствует (`-1`).
- **Идемпотентность:** заполнение выполняется через `SADD` в одном `Pipeline`, поэтому повторная индексация при перезапуске не создаёт дубликатов. После очистки Redis (`FLUSHDB`) и перезапуска индекс полностью восстанавливается из PostgreSQL.

**Токенизация:** текст из полей `title` и `director` приводится к нижнему регистру и разбивается на слова по всем символам, не являющимся буквами или цифрами Unicode. Пустые элементы отбрасываются.

### Кэш поисковых ответов (TTL 3600 секунд)
- **Формат ключа:** `cache:search:<нормализованный_запрос>` (где запрос очищен от пробелов по краям и приведён к нижнему регистру).
- **Тип данных в Redis:** `String` (JSON-массив найденных фильмов).
- **TTL:** `3600` секунд (`1 час`) с момента записи; при чтении TTL не продлевается.
- **Ошибки:** ответы `400` и `500` не кэшируются.
- **Инвалидация:** при пересборке индекса на старте все ключи `cache:search:*` удаляются через `SCAN` + `DEL`.
- **Поведение при кэш-хите:** повторный запрос отдаётся напрямую из Redis без обращения к PostgreSQL (в том числе при временной недоступности БД).

## 6. Логика многословного поиска

Для запросов из нескольких слов используется логика **AND** (пересечение):
- Запрос токенизируется тем же способом, что и при индексации (преведение к нижнему регистру и разбиение на последовательности букв и цифр).
- Для полученных слов формируется список ключей `idx:word:<слово>` и выполняется команда Redis `SINTER`.
- Возвращаются только те фильмы, у которых в `title` и/или `director` присутствуют **все** слова из запроса.
- По найденным `id` актуальные данные фильмов загружаются из PostgreSQL.
- Поиск регистронезависимый, по целым словам. Если совпадений нет, возвращается HTTP `200` и пустой JSON-массив `[]`.

## 7. Примеры запросов

### Поиск фильмов (`GET /search`)

Поиск по названию:
```bash
curl -s "http://localhost:8080/search?q=Solaris"
curl -s "http://localhost:8080/search?q=SOLARIS"
```

Поиск по режиссёру и по нескольким словам:
```bash
curl -s "http://localhost:8080/search?q=Tarkovsky"
curl -s "http://localhost:8080/search?q=Andrei%20Tarkovsky"
```

Пример ответа (`200 OK`):
```json
[
  {
    "id": 1,
    "title": "Solaris",
    "year": 1972,
    "director": "Andrei Tarkovsky"
  }
]
```

Отсутствие совпадений (`200 OK`, пустой массив `[]`):
```bash
curl -s "http://localhost:8080/search?q=nonexistentmovie"
# []
```

Пустой или отсутствующий параметр `q` (`400 Bad Request`):
```bash
curl -i "http://localhost:8080/search"
curl -i "http://localhost:8080/search?q=%20%20%20"
```

### Остальные эндпоинты

```bash
# Загрузка фильмов по диапазону ID из PostgreSQL
curl -s "http://localhost:8080/load-movies?from=1&to=3"

# Последний фильм в каталоге
curl -s "http://localhost:8080/last-movie"

# Swagger UI
open "http://localhost:8080/swagger/index.html"
```
